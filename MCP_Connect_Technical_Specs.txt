2.4 Conversation Lifecycle
End-to-end conversation flow from user message to response.
MESSAGE_RECEIVED: Client sends user message via WebSocket
ANALYZING: LLM analyzes message, generates execution plan
PLANNING: Orchestrator selects MCPs, checks resource budgets
EXECUTING: Parallel/sequential MCP tool calls per plan
AGGREGATING: Collect results from all MCPs, deduplicate, merge
SYNTHESIZING: LLM generates natural language response from aggregated data
STREAMING: Stream response chunks to client via WebSocket
COMPLETE: Persist to DB, clean up resources, ready for next message
Error Handling States:
PARTIAL_FAILURE: Some MCPs succeeded, some failed - return partial results with warnings
TOTAL_FAILURE: All MCPs failed or critical error - return error message to user
CANCELLED: User explicitly cancelled operation mid-execution
TIMEOUT: Conversation-level timeout exceeded (default: 120s)
3. Deterministic Orchestration Rules
Hard rules governing how the orchestrator plans and executes MCP calls. These rules are deterministic and must be followed exactly.
3.1 Planning Rules
3.1.1 MCP Selection
Rule P1: For queries requiring data from category C, select ALL enabled MCPs in category C
Rule P2: If user specifies MCP preference (e.g., &quot;use Sabre&quot;), that MCP MUST be included
Rule P3: If MCP health status is RED, exclude from selection (fallback to remaining MCPs)
Rule P4: Maximum 5 MCPs per query to prevent resource exhaustion
3.1.2 Tool Selection
Rule P5: Within each MCP, select the MINIMAL set of tools needed to answer query
Rule P6: If multiple tools provide same data, prefer tool with lower cost (check tool metadata)
Rule P7: Read-only tools (searches, queries) execute without approval; write tools require approval check
3.2 Parallelism Rules
Rule PAR1: Tools with NO data dependencies execute in PARALLEL
Rule PAR2: Tools within same MCP execute SEQUENTIALLY (one at a time per instance)
Rule PAR3: Tools across different MCPs execute PARALLELLY if rule PAR1 holds
Rule PAR4: Maximum concurrency = min(5, number_of_selected_mcps)
Rule PAR5: If tool B requires output from tool A, A executes first, then B (strict ordering)
Example:
Query: &quot;Find flights and hotels to Paris&quot;
Plan:
- Sabre.search_flights(Paris) [Parallel Group 1]
- Kiwi.search_flights(Paris) [Parallel Group 1]
- Jinko.search_hotels(Paris) [Parallel Group 1]
Execution:
1. Start all 3 in parallel (different MCPs, no dependencies)
2. Wait for all to complete
3. Aggregate results
3.3 Cancellation Rules
Rule C1: User can cancel at ANY time by sending cancel message with message_id
Rule C2: On cancel, immediately stop PENDING and RUNNING tool calls
Rule C3: Completed tool calls are NOT rolled back (idempotency prevents duplicates)
Rule C4: Return partial results to user if some tools completed before cancel
Rule C5: Cancellation must complete within 5 seconds (force kill if needed)
3.4 Timeout Rules
Scope
Timeout
Action on Timeout

60 seconds

90 seconds

120 seconds

3.5 Idempotency Rules
Rule I1: Every tool call MUST include idempotency_key = hash(mcp_id + tool_name + arguments)
Rule I2: Cache results by idempotency_key for 60 seconds
Rule I3: If retrying failed call, use SAME idempotency_key to prevent duplicates
Rule I4: If call with same key is IN_PROGRESS, wait for result instead of duplicate execution

4.2 Enforcement Points

When
Actions

After MCP returns result

Asynchronously after execution
Log to audit trail, trigger alerts, no blocking
4.3 Audit Guarantees
AG1: Every tool call MUST be logged with: timestamp, user_id, mcp_id, tool_name, arguments_hash, result_status
AG2: Every approval request MUST be logged with: timestamp, user_id, action_type, decision, decision_time
AG3: Audit logs are IMMUTABLE: Append-only, never delete, store for minimum 90 days
AG4: Sensitive data (passwords, tokens) NEVER logged: Redact before writing to audit trail
AG5: Audit export available to user: CSV/JSON format, includes all their actions, GDPR compliant
