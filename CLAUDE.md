# Kondi — Multi-LLM Council Pipeline Platform

Tauri desktop app (Rust + React/TypeScript) that orchestrates multi-model "councils" as pipeline workflow steps. Each step spawns a deliberation with Manager/Consultant/Worker roles across any LLM provider.

## Critical Rules

1. **All `Record<Phase|EntryType, ...>` maps in UI must cover BOTH orchestrators.** `DeliberationOrchestrator` and `CodingOrchestrator` use different phases and entry types. Missing entries crash the React tree (no error boundary). Files: `PhaseIndicator.tsx`, `LedgerEntryCard.tsx`, `LedgerTimeline.tsx`, `DeliberationView.tsx`.

2. **Council calls must be stateless, isolated one-shots.** Council/pipeline persona and subagent calls carry NO `conversationId` at all (the former per-call `council-<uuid>` ids were fake — a claude call got `--resume <fake>`). Never add a shared or fabricated conversation/session id to a council call: sharing accumulates context across personas and causes failures in round 2+. Session resumption is chat-only (rule 10). `AgentInvocation`/`AgentResponse` are defined ONCE in `deliberation-orchestrator.ts` and imported by `coding-orchestrator.ts` (it once had a private copy lacking `allowedTools`/`workingDirectory`/`timeoutMs`).

3. **CLI `--allowedTools` is variadic.** Never pass the prompt as a positional arg to `claude` CLI — always pipe via stdin. Positional args get consumed by `--allowedTools`.

4. **Nested CLI spawns must set `CLAUDECODE=undefined` in env.** Without this, inner Claude processes inherit the outer session and conflict.

5. **Worker prompts must check `writePermissions` — but file-writing is GATED BY OUTPUT TYPE, not capability.** When the worker should write files, instruct it to USE TOOLS; the "text-only agent" framing causes workers to describe code instead of implementing it. The decision is made by `effectiveWrite(assignment, outputType)` in `deliberation-orchestrator.ts`: it returns true ONLY when `assignment.writePermissions` AND `outputType` is `'file'` or `'directory'`. For `'string'`/`'json'` (or no output type — a plain deliberation) it returns false, so the worker gets the text-deliverable prompt and emits the actual content instead of narrating fake `write_file(...)` calls. (`canUseTools` is no longer consulted by `effectiveWrite`; it remains only for the runtime tool-exec gate.) **This gating is enforced consistently at both the prompt-framing and tool-grant layers.** `buildWorkerExecutionPrompt` (`prompts.ts`) only uses the tool-exec framing ("EXECUTE THIS TASK NOW using your available tools") for `agent`/`analysis` stepTypes when `permissions?.writePermissions` is true; otherwise it falls through to the text-deliverable framing (previously a tool-less agent was told to use tools it didn't have and narrated fake tool calls — e.g. claiming it wrote `RELEASE_NOTES.md` with no file on disk). The runtime tool GRANT in `invokeAgentSafe` mirrors this: in worker phases (execution/revision/debug), when `effectiveWrite(assignment, outputType)` is false the allowed-tool set is `READ_ONLY_TOOLS` (not `FULL_TOOLS`) — a text-deliverable worker can still research with Read/Grep/Glob but is never offered `write_file`/`Edit`/`Bash`; `code_planning` keeps `PLAN_TOOLS` regardless.

   **Workers receive a typed WORK ORDER, not a bare directive** (see rule 24) — this replaced the old `groundInSource()` (directive + 24000 chars of concatenated source). The manager's directive is two lossy summarization hops from the step's actual input, so `buildWorkOrder` (`src/council/work-order.ts`) re-attaches the task and (deduplicated) source material in fixed sections. The raw problem is held on the orchestrator instance for pipeline runs; when `OrchestratorConfig.brief` is set the orchestrator does NOT overwrite `deliberation.savedProblem` (a BOUND council's saved task used to compound input on each rerun). Without a `brief` (standalone runs) `runFullDeliberation` still persists the problem via `councilStore.setSavedProblem`.

   **`outputType` (and every `DeliberationConfig` field) must be listed in `council/store.ts`'s `createCouncil()` field whitelist, or it silently vanishes on save.** `createCouncil()` builds the persisted `deliberation` object field-by-field (not a spread of `params.deliberation`); `outputType`, `savedProblem`, and `evolveContext` were once missing from that list, so `factory.ts` (and the pipeline executor) could pass them but the STORED council always had `deliberation.outputType === undefined` — making `effectiveWrite` above permanently false and silently forcing every pipeline worker into text mode regardless of the step's configured output type (a review step with `outputType: 'directory'` emitted its files as ```filename: fenced text instead of writing them). Fixed by adding all three fields to the whitelist. When adding a new `DeliberationConfig` field, it MUST also be added there or downstream code that reads it will always see `undefined`.

6. **All stores route through `CouncilDataStore` (in-memory primary, localStorage cache, disk backstop).** `storage-cleanup.ts` exports `councilDataStore` — an in-memory `Map<string,string>` with no size limit. `localStorage` is a best-effort mirror; quota errors are silently ignored. This prevents the browser's 5MB localStorage cap from crashing pipelines. Files using it: `context-store.ts`, `ledger-store.ts`, `council/store.ts`, `pipeline/store.ts`, `session-import.ts`. No council data is ever destroyed — `stripCompletedCouncil` only trims the localStorage copy after artifact extraction; in-memory data remains accessible. **The store also mirrors the FULL value of every council/pipeline key to disk** (durable backstop vs the ~5MB localStorage quota) at `<dataDir>/council-store/<hex(key)>.kv` (hex-encoded key as filename, via the `write_local_file`/`delete_local_file` Tauri commands). Disk writes are debounced (250ms via `armFlush`/`flushDisk`) and flushed on `beforeunload`. `setItem` always schedules a disk write; `setItemDurable(key, value, slim)` writes the FULL value to disk regardless of localStorage quota (localStorage gets the full value, or the `slim()` value if that throws). `hydrateFromDisk()` loads disk → the in-memory Map at startup and migrates any pre-existing localStorage council data to disk once — it's `await`ed in `src/main.tsx` BEFORE the first React render (after `initKondiPaths()`), so a full deliberation (councils + ledger + deliberation state) survives an app restart even when it never fit in localStorage. The store dir is user-configurable in Settings → General → "Council Deliberation Store" (`setDiskDir`/`getDiskDir`/`getDiskDirOverride`/`getDefaultDiskDir`; localStorage override key `kondi-council-store-dir`; default `<dataDir>/council-store`). **This disk store (durable auto-reload of the FULL deliberation) is SEPARATE from a council's per-council "save deliberation" mode (`saveDeliberationMode` full/abbreviated), which exports human-readable markdown to the WORKING directory (`<workingDir>/.kondi/outputs/...` via `deliberationSaveService`).**

7. **`isCouncilType()` excludes gate, script, and condition.** These three step types are not council-based. Script runs a shell command (requires `platform.runCommand`) with `cwd = pipeline.settings.workingDirectory || platform.getWorkingDir()` (`runScriptStep` in `pipeline/executor.ts`) — the same directory council steps write files to, so a script step can operate on files a prior council step produced; the platform dir is only a fallback when no working directory is configured. Condition evaluates an expression and can `skip_next_stage`, `stop`, or `loop_to_stage` (rewind to an earlier stage `loopTargetStageId` and re-run — bounded by `maxLoops`, default 3, per condition step so it can't loop forever). Both use `inputTemplate` for input but have no council/personas.

8. **JSON output type enables `{{input.fieldName}}` templates.** When a step's `outputType` is `'json'`, downstream steps can access individual fields via `{{input.fieldName}}` or `{{input[N].fieldName}}` (dot-path walk). The content must be valid JSON.

9. **No credential fallover between CLI and API.** When a persona specifies `provider: 'anthropic-cli'`, the system must NEVER fall back to `anthropic-api` (or vice versa). All completions go through `llm-router.ts` which dispatches to the correct client based on provider ID. CLI providers (`anthropic-cli`, `openai-cli`) spawn their CLI binaries; API providers use direct HTTP. The `upsertProfile()` function resets failure state when credentials change to prevent stale `failCount` from blocking fresh tokens.

10. **All LLM completions go through `llm-router.ts`.** Chat, council, and pipeline all call `chatCompletion()` or `simpleCompletion()` from the unified router. No call site may import or call a provider client directly for completions. (Provider clients MAY delegate their transport to `src/agent-runtime/` adapters — `openaiCompatibleAdapter`/`anthropicAdapter` — but `llm-router` remains the only completion entry point; the headless CLI's tool-using API path is `cli/api-tool-caller.ts`, rule 23. `relayFetch` lives in `src/services/relayFetch.ts`, same behaviour as before the move out of `openaiCompatibleClient.ts`.) CLI providers use session resumption (`--resume` / `resume --last`) for multi-turn chat; council/pipeline calls are stateless one-shot.

11. **MCP tools for CLI providers go through local proxies.** CLI binaries can't use Kondi's MCP connections directly. The router calls `mcpClient.ensureProxiesForServers()` before LLM calls to start local proxy processes that bridge auth. Proxies are synced to `~/.claude.json` and `~/.codex/config.toml` so the CLI binaries discover them.

12. **Server persistence: Tauri store is source of truth.** User-added servers are persisted via `save_server_config` (Rust backend → `~/.local/share/kondi/servers.json`). localStorage is a cache that gets rebuilt from Tauri on startup. The startup flow loads Tauri first, merges localStorage second, registers built-ins third, then auto-reconnects — this order prevents race conditions that overwrite localStorage with incomplete data.

13. **Routed profiles are pseudo-models, resolved in `llm-router` before dispatch.** The "Smart Router" (`src/router/`) exposes seven budget profiles (`balanced`, `quality`, `cheap`, `orchestra`, `best-value`, `zai`, `nvidia`) as selectable models with id `route:<profile>` and provider `'router'` (`ROUTED_PROFILE_OPTIONS`). The `nvidia` profile (`allowedProviders: ['nvidia-router']`) pins dispatch→`nvidia/nemotron-3-ultra-550b-a55b`, discuss→`nvidia/nemotron-3-super-120b-a12b`, execute→`z-ai/glm-5.2`, reflect→`deepseek-ai/deepseek-v4-pro`, compress/state_update→`nvidia/nemotron-3-nano-30b-a3b` — all served via NVIDIA NIM, budget numbers mirror `zai`. When `chatCompletion()`/`simpleCompletion()` see a routed model, they call `resolveRoutedModel(profile, phase, prompt)` to get a concrete `{provider, model}`, then dispatch normally. Pass `routePhase` (a `LedgerPhase`) from the call site — orchestrator invokers derive it from `persona.preferredDeliberationRole` via `roleToPhase()` (manager→dispatch, consultant→discuss, worker→execute, reviewer→reflect); chat defaults to `discuss`. **Pure helpers (`isRoutedModel`, `roleToPhase`, `ROUTED_PROFILE_OPTIONS`) live in `router/profile-options.ts`** — import those from selectors/CLI, NOT `router/resolve.ts` (which pulls in webview-only `simpleCompletion` + `auth-profiles`). The CLI has its own resolution in `cli/llm-caller.ts`. The learned NN tier from kondi-chat is intentionally not ported (needs offline-trained weights). **Profiles are user-manageable** (Settings → Routing, `RouterProfilesSettings.tsx`): `router/profile-store.ts` persists custom/edited profiles (localStorage `kondi-router-profiles`) layered over `BUILTIN_PROFILES`; `getEffectiveProfile()`/`getMergedProfiles()`/`getProfileOrder()` expose the merge. `resolve.ts` resolves via `getEffectiveProfile()` (custom > built-in), so added/edited profiles route everywhere. Dropdowns call `getRoutedProfileOptions()` (dynamic, merged) and re-render on `ROUTER_PROFILES_EVENT` via the `useRouterProfilesVersion()` hook — wired in ChatArea, AddPersonaModal (also covers the pipeline step picker), and RoleAssignment. So added/edited profiles appear in every model dropdown live, no reload.

14. **Broken models are auto-hidden, not removed from the catalog.** `modelProbe.ts` remembers per-model availability (localStorage `kondi-model-status`) so selectors never offer a model the user's account/plan can't use (e.g. a ChatGPT Codex account rejecting `gpt-5.3-codex`). Policy = **hide only proven-broken**: a model is hidden ONLY if a probe/live call definitively failed it (`classifyModelError → 'broken'`: "not supported"/"not found"/invalid/404/400-with-model); untested, last-known-good, and soft-failed (auth/network) models stay visible. Two triggers: (a) AUTOMATIC — `chatCompletion()` wraps its dispatch and calls `recordModelCallFailure(model, prov, err)` on throw (and `recordModelCallSuccess` clears stale flags on success); (b) MANUAL — the "Refresh models" button in `ProviderSettings` calls `probeAllModels()` (tiny one-shot per configured-provider model, concurrency 4). Selectors filter via `filterVisibleModels()` and subscribe via the `useModelStatus()` hook (`ChatArea`, `AddPersonaModal`, `RoleAssignment`; pipeline persona picker reuses `AddPersonaModal`). The catalog (`config/models.ts`) is never mutated. **CLI model IDs (`OPENAI_CLI_MODELS`, `CODEX_MODELS`) are verified against the installed Codex binary (v0.139.0: `gpt-5.5`/`gpt-5.5-pro`/`gpt-5.4`/`gpt-5.4-mini`/`gpt-5.4-nano`/`gpt-5.3-codex`/`gpt-5.2-codex`); default `openai-cli` model is `gpt-5.5`.** The stale `gpt-5.1`, `gpt-5.1-codex-max`, and `gpt-5.1-codex-mini` SKUs were removed from the catalog (`config/models.ts`), the Codex client list (`codexClient.ts`), and the CLI→API fallback map; all council/pipeline defaults that pointed at `gpt-5.1-codex-max` (CouncilLibrary, StepConfigPanel, templates) now point at `gpt-5.5`. Refresh these when `codex update` bumps the set. **DeepSeek catalog uses the live V4 names `deepseek-v4-pro` (default, featured) and `deepseek-v4-flash`** — the old `deepseek-chat`/`deepseek-reasoner` are legacy aliases (still work, no longer advertised by `/models`). **NVIDIA catalog (`NVIDIA_MODELS`) holds 7 curated models** verified live against the hosted NIM `/models` endpoint + tested through the app's real request shape (streaming, with and without tools): `nvidia/nemotron-3-super-120b-a12b` (default, featured), `nvidia/nemotron-3-ultra-550b-a55b` (featured), `deepseek-ai/deepseek-v4-pro`, `z-ai/glm-5.2`, `nvidia/llama-3.3-nemotron-super-49b-v1.5`, `openai/gpt-oss-120b`, `nvidia/nemotron-3-nano-30b-a3b` — all 0-cost with `costDisplay: 'NIM'` (NVIDIA API keys are credit-based, not per-token USD). Deliberately excluded despite appearing in the live `/models` list (verified broken 2026-07): `moonshotai/kimi-k2.6` (404 "Function not found"), `meta/llama-4-maverick-17b-128e-instruct` (request hangs), `qwen/qwen3.5-397b-a17b` (hangs on any real completion, streaming or not — tiny probes pass), `minimaxai/minimax-m3` (works non-streaming but streaming returns instant "Internal server error", and chat always streams). Listed-but-broken is common on NIM — test STREAMING with real token counts before adding a model, not just a tiny non-streaming probe. `nvidiaRouterClient` (`openaiCompatibleClient.ts`) and the CLI `nvidia-router` path (`cli/llm-caller.ts`) now default to the hosted `https://integrate.api.nvidia.com/v1` (was `http://localhost:8001/v1`); `VITE_NVIDIA_ROUTER_URL`/`NVIDIA_ROUTER_URL` still override for a local NIM/router deployment. Provider display name is `NVIDIA NIM` (was `NVIDIA Router`) in `useProviderConfig.ts`, `RoleAssignment.tsx`, and `ChatArea.tsx`. **NIM's API sends NO CORS headers** (unlike Z.AI/DeepSeek), so the webview cannot call it directly — every request dies as "Connection error". Webview NIM calls therefore route through the `http_relay_stream` Tauri command (Rust reqwest = no CORS; HTTPS-only), which forwards response bytes over an IPC channel AS THEY ARRIVE — `relayFetch` in `openaiCompatibleClient.ts` adapts the channel to a fetch `Response` for the OpenAI SDK, enabled per-client via `relayViaBackend` (set only for the hosted NIM URL; a local `http://` override calls directly). Do NOT "simplify" this to the buffered `http_relay` command (kept for one-shot use): buffering the full body trips the chat's 90s no-first-byte watchdog on long generations and kills live token streaming. The CLI path needs no relay (Node has no CORS).

15. **Claude CLI write containment is enforced by a PreToolUse hook, never by Claude Code's permission flags.** Council workers run the `claude` binary with `bypassPermissions` + full tools, so without a guard they can write ANYWHERE — a worker once resolved a "docs/" directive against the parent kondi git repo and wrote into the real project `docs/`, escaping its `directoryConstrained` working dir. Empirically (headless `--print`): `--permission-mode acceptEdits` still writes escapes, absolute `--allowedTools "Write(//abs/**)"` rules silently fail to match, and `bypassPermissions` disables confinement entirely. The ONLY reliable mechanism is a `PreToolUse` hook (fires under every permission mode), and getting it to actually fire took three non-obvious fixes (an inline `node -e` hook silently never ran — confirmed via the raw claude stream; the writes escaped). `src/services/cli-workdir-guard.ts` exports `WORKDIR_GUARD_SRC` (the guard script) + `workdirGuardSettings(command)`; the hook (matcher `Write|Edit|MultiEdit|NotebookEdit|Bash`) **denies any write outside the working dir** (root = `KONDI_WORKDIR` env, fallback hook payload `cwd`); Bash redirects/mutations to absolute paths outside the dir are blocked (reads allowed). **The three mechanics:** (1) the guard MUST be a `.cjs` FILE invoked as two UNQUOTED tokens `<node> <file>` — claude splits the hook command on whitespace with no shell, so an inline quoted `-e "…"` is mangled and never runs; (2) the first token MUST be the ABSOLUTE node path (`process.execPath`) — claude sanitizes the hook PATH and a bare `node` (nvm/volta) is not found → falls open; (3) allow = `exit 0` silently (explicit `permissionDecision:'allow'` interfered with in-sandbox writes), deny = emit JSON. `cli/claude-caller.ts` writes the file + passes `process.execPath`; `src/services/claudeCliClient.ts` (webview) installs it via the `run_command` Tauri backend. Do NOT rely on the system-prompt "working directory override" text — it is advisory only. **`run-council.ts` also `git init`s the working dir** so the Claude CLI's nearest-git-repo discovery stops there instead of adopting a parent project (e.g. the kondi repo) — without this the worker explores the parent tree for minutes (timeouts) and resolves relative paths against the parent root (escape). The guard file is written atomically (temp+rename, once/process) so concurrent calls can't read a truncated guard and fail the hook open. The `openai-cli` (Codex) path needs no hook — `--full-auto` (`--sandbox workspace-write`) confines it natively, UNLESS the user enables the "Run Codex without its OS sandbox" toggle (Settings → General → "CLI Workers"; localStorage `kondi-codex-no-sandbox` for the webview / env `KONDI_CODEX_NO_SANDBOX=true` for the CLI). That swaps `--sandbox workspace-write`/`--full-auto` for `--dangerously-bypass-approvals-and-sandbox` — for hosts that restrict unprivileged user namespaces (recent Ubuntu/AppArmor) where Codex's bwrap sandbox can't init. Containment then relies ONLY on Kondi git-scoping the working dir (less strict; warned in the UI). Read in `src/services/codexCliClient.ts` (webview) and `cli/codex-caller.ts` (CLI). Claude Code needs no equivalent: it has no OS sandbox / userns dependency (it uses `bypassPermissions` + the PreToolUse guard hook). **The guard is a STANDALONE crate at `src-tauri/kondi-guard/` (serde_json + std only, `license = MIT`), a Cargo WORKSPACE member (`src-tauri/Cargo.toml` `[workspace] members = ["kondi-guard"]`) sharing the `src-tauri/target` dir.** Splitting it out fixes a chicken-and-egg: building the guard as a `[[bin]]` inside the Tauri crate ran `tauri-build`, which validates the `externalBin` sidecar that the build is itself trying to produce (and needs GTK/webkit). `build-guard.sh` and `.github/workflows/ci.yml` now build it via `cargo build -p kondi-guard` (fast, no tauri-build). The guard SOURCE/behavior is unchanged.

The "Refresh models" button ALSO runs `modelCatalogSync.ts` for API providers: it fetches each provider's live `GET /models` list (via the clients' existing `listModels()`) and reconciles vs the catalog → `confirmed` / `staleInCatalog` / `missingFromCatalog` (persisted to `kondi-catalog-sync`). This is the API-side equivalent of reading the Codex binary's model list, and is **advisory only** — it surfaces drift but never hides a model itself (the live probe remains the sole authority for hiding, since `/models` lists can be incomplete). Discoverable providers: `anthropic-api`, `openai-api`, `deepseek`, `xai`, `zai`, `moonshot`, `nvidia-router`, `ollama` (Google/cloudcode-pa and CLI providers are excluded).

16. **Every council type runs the SAME deliberation workflow — there is no workflow-skipping "lightweight" path.** `agent`/`analysis` used to short-circuit to a single worker pass (silently ignoring configured consultants); that shortcut is removed. A "lightweight" council is just a SMALLER council (e.g. 2 consultants), never one that skips phases. The deliberation stays cheap on its own: with 0 consultants it skips the discussion rounds and goes straight to deciding, and round/revision counts cap depth. The only remaining direct-execution path is the structural manager-less case (no manager → can't orchestrate). Related: **`getPersonaByRole()` dedupes by personaId** so a persona with a duplicate role assignment can't deliberate/review twice (which showed the "same response" twice in the ledger). **The CODING orchestrator (`coding-orchestrator.ts`) also honours consultants now** — `consultOnPlan()` runs an advisory pass BETWEEN decompose and implement: each assigned consultant (`getPersonaByRole(council,'consultant')`) reviews the decomposed plan with NO tools (`invokeAgentSafe` context `'consultation'` auto-sets `skipTools`), recorded as a consultant `'analysis'` ledger entry under the `'decomposing'` phase (both already in the UI maps), and their guidance is folded into the implementation spec. No consultants → no-op.

17. **Coding councils complete HONESTLY (no false success) and list the files they produced.** In `coding-orchestrator.ts` `mergeAndComplete()`: the council phase is set to `'failed'` (a mapped terminal phase — added to the `validNext` of `implementing`/`code_reviewing`/`testing`/`debugging`) instead of `'completed'` when there are ZERO module outputs OR the merged output is self-reported blockage (`looksLikeFailedDeliverable` heuristic — requires 2+ strong failure markers AND a body <4000 chars). So a worker that narrates being blocked (sandbox/tooling/filesystem) yields a FAILED council, not a false success. The coding output artifact + completion summary both start with a `## Files produced (N)` section listing the worker's ACTUAL changed files from `git status --porcelain` (`listChangedFiles`), not its prose. To guarantee the diff works, `createGitSnapshot` compares `git rev-parse --show-toplevel` against the working dir (trailing-slash-normalized) and `git init`s the working dir as its OWN repo (+ sets a local git identity) unless it's already the top-level — matching the CLI path (rule #15). **An earlier version instead checked `git rev-parse --is-inside-work-tree`, which is also true when the working dir is merely NESTED inside another repo** (e.g. an examples workspace living inside the kondi repo itself) — so `git add -A && git commit -m "kondi: pre-pipeline snapshot"` committed the PARENT project's entire tree into the parent's git history (observed: junk snapshot commits swept up unrelated uncommitted work on the kondi repo's own main branch). Same failure class as the CLI nearest-repo escape in rule #15. `ensureWorkspaceDir` also pre-creates `<workingDir>/.kondi/workspace` via `runCommand` (Tauri backend, outside the CLI sandbox) before the worker runs, since a sandboxed CLI worker often can't mkdir it.

18. **Launch-time model/provider validation THROWS on unusable persona models — it does NOT substitute.** `src/council/model-validation.ts` `validateCouncilModels(council, configuredProviders)` runs in `useCouncilHandlers.ts` `onFrameProblem` BEFORE the deliberation/coding workflow starts (both paths). It throws a detailed `Error` (listing each offending persona's name, model, provider, and reason) if any persona model is unknown (removed from the catalog), proven-broken (`modelProbe.isModelBroken`), OR whose provider isn't configured — blocking the launch so the user fixes their setup deliberately. Routed personas (`provider:'router'` / `model:'route:*'`) are left as-is (resolved later in `llm-router`). **An earlier version SWAPPED unusable models for a cheap working fallback and persisted the swap; that was deliberately removed** — silent substitution can route a council to a different (and differently-priced) model than the user picked, so it now fails fast with an actionable error instead. (`ModelValidationError` carries `personaName`/`model`/`provider`/`reason`; the old `ModelSubstitution` type and `pickWorking`/`FALLBACK_PROVIDERS` fallback chain are gone.)

19. **Condition steps can `loop_to_stage` (bounded iterative councils).** A `condition` step's action can rewind flow to an earlier stage (`loopTargetStageId`) and re-run from there — refine→review→refine. Bounded by `maxLoops` (default 3) PER condition step via an in-run counter (`loopCounts`) in the executor; once the budget is exhausted, behavior is governed by `onLoopExhausted` (default `'continue'`: proceed with the last attempt; `'stop'`: end the pipeline as completed; `'fail'`: throw, failing the step). The executor resets the intervening stages to `pending` and rewinds the stage loop; the condition's evaluated input rides the back-edge as **feedback** on the loop target's next artifact list ("THIS IS A RETRY (attempt N)...") so the target knows why it was sent back. Loop target must be an earlier (or same) stage — validated pre-run by `pipeline/step-validation.ts` (`validatePipeline()`, powers ⚠ badges + a run-blocking banner in the builder). UI: `StepConfigPanel` exposes the action + target-step picker + budget + exhaustion outcome.

20. **Subagents are provider-agnostic worker fan-out (`docs/SUBAGENTS.md`).** A `Persona` can carry `subagents: SubagentSpec[]` (name + ANY `provider`/`model` + `task` + optional `systemPrompt`). In `deliberation-orchestrator.ts` `executeWork`, `runSubagents(council, worker, directive)` runs them in PARALLEL before the worker's own call — each via `invokeAgentSafe` with a SYNTHETIC persona carrying the subagent's provider/model, so dispatch goes wherever that model lives (the whole point: not Claude-only). Each result is a ledger `analysis` entry under `executing` (rule #1-safe); the combined findings are folded into the worker's directive (`SUBAGENT FINDINGS`) and the worker synthesizes. Bounded to 4, tools off, failures non-fatal. Fan-out is wired into the WORKER (`executeWork` + `runDirectExecution`) AND the MANAGER decision (`makeDecision`). **Dynamic spawning (v2):** when `persona.dynamicSubagents` is set, `planDynamicSubagents` does a planning call asking the persona to propose up to 3 subagents (`NAME | provider/model | task`, `self` = reuse own model) which then run via the same engine — so a worker/manager can decide its own helpers at runtime, each on any provider. Config UI: a "Subagents" section in `AddPersonaModal` (per-row any-provider model picker + task, plus a "spawn dynamically" toggle) for worker + manager. Reviewer fan-out is the remaining roadmap item.

21. **Councils have no standalone UI surface — every council lives inside a pipeline.** The sidebar's Councils section and `CouncilLibrary` (component + CSS) are deleted (its shared `.council-table`/`.ct-*`/`.crd-*` styles moved into `PipelineLibrary.css`); Pipelines is the single top-level surface. The `'council'` `AppView` still exists but is reachable ONLY as a deliberation drill-in from a pipeline step or a project's council list — its Back button always returns to `'pipelines'` (`App.tsx`), never re-shows a council grid. `pipeline/council-migration.ts` keeps every council reachable: `migrateCouncilsToPipelines()` runs once at startup (`main.tsx`, right after `hydrateFromDisk()`) and gives each standalone council a deterministic one-step pipeline bound to it (`council-1s-<councilId>`, step `config.boundCouncilId = councilId`), while promoting multi-step council-workflow shadow pipelines (`council-wf-<workflowId>`, built by `workflow-runner.ts`'s `syncWorkflowPipeline`) from hidden to canonical (the `source !== 'council-workflow'` filters were removed from `Sidebar.tsx`/`PipelineLibrary.tsx`). `ensurePipelineForCouncil(councilId)` (exported, idempotent) MUST be called anywhere a council is created outside a pipeline run — the chat-generated-council handler (`COUNCIL_RUN_EVENT` listener in `App.tsx`) and a project's "+ New council" button both call it — otherwise the new council is orphaned with no UI path to it. **A bound step's own `councilSetup` is an intentionally empty shell** — the council record is the sole source of truth for personas/task/config. `StepConfigPanel.tsx` exports `BoundCouncilStepPanel` (a live read-only persona/task summary + "Open deliberation & edit" button), rendered by `PipelineBuilder` INSTEAD OF `StepConfigPanel` whenever `step.config.boundCouncilId` is set — kept as a separate component so the two panels' hook order can never mix. `pipeline/step-validation.ts`'s `validateCouncilStep` short-circuits to `validateBoundCouncil(councilId, configuredProviders)` — checking the LIVE council's personas/providers — whenever `boundCouncilId` is set; validating the empty shell instead would wrongly flag every migrated council with "No personas configured" and block it from ever running. Because bound steps skip the executor's normal council-creation path, `usePipeline.ts`'s `handlePipelineRun` also runs `validateCouncilModels()` (rule 18 semantics — throw, never substitute) against every bound council up front, before invoking the executor.

22. **Self-improvement loop (`src/improve/`, SPEC §4f): metrics are always on, the LLM loop is opt-in, and nothing it does blocks or mutates a run.** **Metrics:** `PipelineExecutor.finishRunHook` runs after every completed AND failed (never aborted) run → `buildRunScorecard` (`run-metrics.ts`, no LLM, built from the ledgers) → `improveStore.saveScorecard` (councilDataStore key `scorecard-<pid>-<runId>`, index in `improve-<pid>`, capped `MAX_SCORECARDS`=50) + `<runDir>/_scorecard.json` + `<wd>/.kondi/memory/<pid>_scorecards.jsonl` (full history; `getNextRunNumber` also reads it). Per-call data is the CONCRETE model: `LedgerEntry` carries optional `model/provider/inputTokens/outputTokens/attempts/routed`, attached by both orchestrators' `invokeAgentSafe` as `response.structured.callMeta` and lifted by `createEntry` (no new entry types/phases — rule 1 untouched). Any new LLM call path must keep populating `provider/model/inputTokens/outputTokens` on `AgentResponse`/`CallerResult` or scorecard cost/model data silently goes blank. **Opt-in cycle:** `Pipeline.settings.selfImprove` (`SelfImproveSettings`, defaults `DEFAULT_SELF_IMPROVE`, always read through `withSelfImproveDefaults`) gates `runImprovementCycle` (`cycle.ts`): retrospective → proposals (+ lessons as `lesson` proposals) → optional eval → auto-apply or queue. It never throws and never changes the run status. **Retro/judge/replay are ordinary councils** named `[Improve] …` (`RETRO_COUNCIL_PREFIX`) created via `createCouncilFromSetup` with `pipelineId` set (they have a home — rule 21 — and don't surface as orphans); retro = worker-only (`stepType:'council'`, `outputType:'json'`, `maxRounds:0`; `deep:true` adds a manager + 2 consultants). **Gotcha: the orchestrator works from the RAW PROBLEM it is handed, not the council `task`** — so the retro instructions are joined into the raw problem together with the evidence bundle (`${task}\n\n---\n\n${bundle}`); putting the task only in the factory's `task` makes the model never see it. `pruneImproveCouncils` deletes the oldest `[Improve]` councils beyond `maxRetainedRetros`. **Replay NEVER goes through a second `PipelineExecutor`** (`eval.ts` `replayStep`): it uses `createCouncilFromSetup` + `DeliberationOrchestrator` directly on the recorded `StepInputRecord` (`step-input-<councilId>`, written by the executor for bound AND unbound steps, also as `_input.md`), tool-less, no working directory — no library/run-dir/memory side effects. Judging is a worker-only `[Improve] Judge` council, blind and position-swapped (A/B then B/A; disagreement → 0.5); `total = 0.7·judge + 0.3·mechanical`. Coding steps and bound councils are `judge-only` (v1, no replay). **Manual mode is NON-BLOCKING:** proposals are queued and the run (and CLI process) finish normally; background/scheduled runs never approve anything. **Mode is re-read LIVE** (`liveSettings()`) at hook time and again before EACH auto-apply, so flipping auto→manual mid-cycle stops further applies; auto also requires `score.total >= autoApplyMinScore` when an eval ran. **Apply/revert (`apply.ts`):** unbound steps mutate via `pipelineStore.updateStepConfig` only after `validateStep` (only NEW problems block); bound steps go through `councilStore` (Zod throws → proposal `rejected`). Staleness = `configHash` mismatch AND the field-level rebase check (`isApplicable`: still applicable if the exact field still equals the proposal's `before`, so sibling proposals from one retro don't invalidate each other); `appliedConfigHash` makes revert refuse if the target changed since. `worker_prompt` must contain `## COMPLETION SUMMARY` and sets `suppressPersona:false` atomically (else the minimal worker prompt would ignore the new prompt). `router_profile`/`structure` kinds parse but `applyProposal` marks them `invalid` (unimplemented); `model_swap` is gated off by default (`scope.models`) and does NOT yet run rule-18 `validateCouncilModels`. **Lessons** are injected at the ORCHESTRATOR level: the executor builds `OrchestratorConfig.lessons` (`buildLessonBundle`, role-scoped, capped `lessons.maxChars`), and both orchestrators append a `LESSONS FROM PREVIOUS RUNS` block (`formatLessonsBlock`) to every persona's user message right AFTER the word-limit injection — so they also work for bound councils whose records must not be mutated per run. Lessons persist in the improve store and are mirrored to `<wd>/.kondi/memory/<pid>_patterns.json` as a SUPERSET `{patterns, lessons, updatedAt}` — `patterns` stays a string[] so `{{memory.patterns}}` keeps working; never narrow that shape. New councilDataStore key prefixes `improve-`, `scorecard-`, `step-input-` are registered in `storage-cleanup.ts` and carried by session export/import (`KondiSession.improve`, `KondiSessionCouncilData.stepInput`). CLI: `kondi improve <pipeline.json|id> [--runs N] [--eval none|judge|replay] [--retro-model prov/model] [--deep] [--auto-approve] [--write-back [file]] [--status]` and `kondi pipeline … --improve [--auto-approve]`. **Seat self-view (SPEC §4a-1):** `scoreStep` stores `StepScore.reviewFeedback` (≤12 lines, ≤300 chars each: revision_request/re_deliberation heads, code_review issue descriptions, failing test_result tails — bound ledgers are wiped per run, so the scorecard is the durable record). When `lessons.enabled`, the executor calls `buildSeatBriefs(cards, stepId)` (`improve/seat-brief.ts`, needs ≥2 prior runs of that step; ≤600 chars/role) on `improveStore.listScorecards(pipelineId, 10)` and passes `OrchestratorConfig.seatBriefs`. The WORKER brief renders in the work order ("## Your track record in this seat") / coding module directive; the MANAGER brief is injected ONLY in the `directive` context — never framing/review.

23. **Agent runtime: API/local-model workers get a REAL tool loop (`src/agent-runtime/`).** `runToolLoop` (`tool-loop.ts`) is provider-neutral (max turns, per-tool timeout, result cap + older-result compression, summed usage; tool failures become error tool-results, never throws) over a `ToolRegistry` (short wire names, schema minimization), an SSE parser (`sse.ts`), and adapters `openaiCompatibleAdapter` / `anthropicAdapter` (`adapters/`, both take `fetchImpl` so tests/relays inject transport). Cancellation helpers live in `signals.ts` (`AbortError`, `TimeoutError`, `anySignal`, `timeoutSignal`, `withSignal`). Node local tools (`node/local-tools-node.ts`: Read/Write/Edit/Bash/Glob/Grep) are CONTAINED: `node/path-containment.ts` realpath-resolves every path and DENIES reads AND writes outside the working dir (rejects `dir/../x`, symlinked dirs/files), and `node/command-rules.ts` applies guard-equivalent Bash rules (a fixture test asserts agreement with `WORKDIR_GUARD_SRC`, rule 15). `cli/api-tool-caller.ts` (used by `cli/llm-caller.ts`) runs this loop for the CLI's API providers (`anthropic-api`, `openai-api`, `deepseek`, `xai`, `zai`, `moonshot`, `nvidia-router`, `ollama`), scoped by the orchestrator's abstract `allowedTools`, returning real summed usage — so headless pipelines on API models can read/write files inside the working dir (REPORT #5 closed). Both CLI runners now report `canUseTools` true for every provider except Gemini (`PipelineExecutorCallbacks.canUseTools` is forwarded to BOTH orchestrators). Do not re-introduce single-shot callers that advertise tools the provider cannot run. `claudeCliClient.ts` (GUI) passes `--allowedTools` scoping, a real per-call timeout and real usage. Tests: `mcp-connect-mvp/tests/` (vitest: `tests/council`, `tests/agent-runtime`, `tests/improve`); `npm run typecheck` checks app (`tsconfig.app.json`) AND CLI (`tsconfig.cli.json`).

24. **Worker WORK ORDER, signals, ask-back, and honest failure (`src/council/`).** `buildWorkOrder` (`work-order.ts`) composes every worker prompt (`executeWork`, `requestRevision`, `runDirectExecution`) from fixed sections: Objective (step task alone), Deliverable, Acceptance criteria (full section via heading-aware `extractAcceptanceCriteria`), Directive, Constraints (tool scope; never names write tools for a text deliverable — rule 5), Verification, Attempt (N of M, prior output + reviewer feedback + Q&A), Inputs from earlier steps, Source material, plus `WORK_ORDER_PROTOCOL`. The per-run `OrchestratorConfig.brief` (`StepBrief`: task, stepName, stepType, runDir, inputs) is supplied by the executor — it is NOT a `DeliberationConfig` field (so no `createCouncil()` whitelist entry). **Signals** (`worker-signals.ts` `parseWorkerSignals`): `## NEEDS INPUT` + `**Question:**` (worker STOPS), `**Status:** Blocked — reason`, `**Verification:** exit N`; a question alongside `**Status:** Complete` is a caveat, not a stop. Stored as `structured.signals` on `work_output`/`module_output` entries (no new entry types — rule 1). **Ask-back** (`ask-back.ts`, `handleWorkerSignals` at all three worker call sites; coding has its own for `module_implementation`/`debug_fix`): ladder manager (LLM, JSON `{answer|escalate}`, manager context `worker_question`) → human (`OrchestratorConfig.onWorkerQuestion`, wired from `PipelineExecutorCallbacks.onCouncilQuestion`) → `AUTO_ANSWER`; `MAX_QUESTIONS_PER_PHASE`=2 then `BUDGET_EXHAUSTED_ANSWER`. Ledger: question = `manager_question` authored by the WORKER; answer = `response` with `structured.answeredBy` (`manager|user|system`); the worker is re-invoked on the SAME attempt (`attempt.mode:'answer'`). **Blocked** workers are never quality-reviewed: `reviewWork` synthesizes `re_deliberate` once (blocked reason as new information), then a best-effort `revise`, then `failed` (error entry + thrown → failed step); manager-less blocked → error + `failed` + throw. `PHASE_TRANSITIONS`: `executing`/`reviewing`/`revising` may go to `failed`. Pipeline side: `PendingInput {kind:'gate'|'question', prompt, councilId, personaName, managerNote, askedAt}` on `PipelineStep.pendingInput` (set via `pipelineStore.setStepPendingInput`; cleared by `resetStaleExecutionStates` and when input arrives); the step is parked in `waiting_approval` while a question is pending, then restored to `running`. GUI: `WorkerQuestionCard` in `PipelineExecutionView` ("Answer" / "Let the worker decide"); background runs answer null. CLI: `run-pipeline` `promptQuestion` / `run-council` `onWorkerQuestion` read from the terminal ONLY when stdin is a TTY (else worker proceeds on best judgment). **Honest outcomes (Phase 0):** a council ending in `failed`/`paused`/`cancelled` FAILS its pipeline step (partial artifact metadata `terminalPhase`) instead of feeding "FAILED …" text downstream; `abort()` also fails steps parked in `waiting_approval`; `maxRevisions` uses `?? 3` (configured 0 means 0 — never `|| 3`); coding verification that cannot run (no `runCommand`) is SKIPPED with a warning, never a fake pass; standalone `runCommand` adapters use the `workingDir`/`exit_code` shape (not `cwd`/`exitCode`) so tests no longer always read as failing outside pipelines; the Node platform `runCommand` is an async spawn with process-group kill + output cap.

25. **Worker-owned verify loop (`deliberation-orchestrator.ts`).** `WorkerPermissions.verifyCommand`/`verifyMaxTries` are threaded in by `withVerify` ONLY when the worker has write permissions (rule 5 — text workers never see them). `resolveVerifyCommand` order: `OrchestratorConfig.verify` (`{command, autoDetect, maxWorkerTries}`) → `deliberation.testCommand` → `detectTestCommand` (`pipeline/test-detect`) for `file`/`directory` outputs (cached per council). `reviewWork` runs `runFinalVerification` BEFORE any manager LLM call and writes a `test_result` entry (`structured {exitCode, testCommand, verification:true}`). Failure → a mechanical synthesized `revise` (0 tokens, `structured.automatic:true`) carrying the test tail, SKIPPING consultant + manager calls (`requestRevision` then issues a `fix` work order); pass → a VERIFICATION section in `buildManagerReviewPrompt`. Manager-less direct execution verifies and gets `maxRevisions` bounded fix attempts. The coding orchestrator resolves install && build && test BEFORE `implementModules` and threads it into module/revision/debug permissions (module directive says RUN `<cmd>`); the final test loop reuses it. `StepConfigPanel` shows the Test/Verify command for ANY file/directory-output step (debug/review-cycle fields stay coding-only). Coding module workers get the spec head (6000 chars) + testStrategy and per-module filtered review issues (`structured.issues` on `code_review`); the debug prompt embeds ACTUAL file contents via `readFile`, not the earlier prose.

26. **Cancel vs budget vs failure vs stream (SPEC §4a-4/§4a-5/§5b).** Three distinct terminal outcomes: `cancelled` = USER abort only (`cancellation` ledger entry, NO `error` entry, NOT `failed`, `finishRunHook` skips it so NO scorecard); `failed` = error, blocked worker, or BUDGET breach (`error` entry, scorecard IS written); a TIMEOUT is never a cancel — it is retried once (both orchestrators) then fails. Mechanism: the executor owns a run-level `AbortController` (`runAbort`); its signal reaches both orchestrators (`OrchestratorConfig.signal`/`CodingOrchestratorConfig.signal`) and races pending gate/question prompts. Both `invokeAgentSafe` compose `anySignal([run signal, timeoutSignal(timeoutMs)])` PER ATTEMPT, pass it to the invoker (`AgentInvocation.signal`) AND race it (`raceSignal`, `agent-runtime/signals.ts`) because some transports ignore signals; abort is classified FIRST and never retried (even if the message says "terminated"). `throwIfAborted` at phase boundaries; consultant fan-outs and coding per-module/review/debug catches MUST rethrow aborts (never swallow them). `markCancelled` is idempotent; every non-terminal phase may go to `cancelled` AND `failed` in BOTH `PHASE_TRANSITIONS` tables (an error escaping the phase loops, e.g. during framing, leaves the council `failed`). Do not reintroduce a `Promise.race` timer (`gui-caller`'s `withTimeout` is gone). Claude CLI cancel = `cancel_claude_streaming` Tauri command (cancel-id registry; `run_claude_streaming` takes `cancel_id`); anthropic/gemini (buffered Rust transports) only check the signal between tool turns. **Budget (`Pipeline.settings.budget`, `pipeline/budget.ts`):** a breach is an HONEST FAILURE, never a cancel — `isUserAbort` MUST exclude `BudgetExceededError` (also when it is the signal reason under `abort_now`), producing an `error` entry with `structured.budget {kind, usd, tokens}` + `failed`; the stage loop throws "Budget exceeded" before the next stage (steps `skipped`). Any new orchestrator abort check must go through `isUserAbort`, not `signal.aborted`. **Usage:** token counts come from `pickUsage` (`services/usage.ts`: `billedInputTokens` → last-turn input → chars/4 with `reported:false`); new clients must report usage summed across turns. **Streaming is DISPLAY ONLY:** `AgentInvocation.onEvent` / `onAgentEvent` events (and `createStreamJsonAccumulator` in `output-parsers.ts`) feed the live tail; the final text MUST still come from `parseStreamJsonOutput` over the full output (its top-level `content_block_delta` branch was removed so text never doubles) — never build results from stream events. **Tauri gotcha:** Tauri `Channel<T>` params cannot be `Option` — `run_claude_streaming`'s `on_line: Channel<String>` is REQUIRED, so the webview client always passes a channel (a no-op when nobody listens).

27. **Worktree mode (`CouncilStepConfig.codebaseMode: 'worktree'`, SPEC §4a-6, `pipeline/worktree.ts`): workers NEVER commit — the EXECUTOR does.** A worktree step runs in `<repo>/.kondi/worktrees/<run12>-<stepSlug>` on branch `kondi/<pipelineSlug>/<run12>` (collision → `-2`…). Invariants: (1) precondition = the pipeline working dir IS a git repo top-level (`isRepoTopLevel`, same nested-repo hazard as rules 15/17); otherwise the executor logs and falls back to isolated, and `validateStep` flags worktree mode without a pipeline working dir. (2) `.kondi/` is excluded via `.git/info/exclude` (`ensureKondiExcluded`, never `.gitignore`) so run artifacts stay out of diff/commit. (3) Workers edit IN PLACE and must not commit/stash/checkout (`WorkerPermissions.codebase`) — Codex's sandbox roots at cwd, so a worktree commit would need to write `<main>/.git`. After the step the executor ALWAYS commits (also on failure, message tagged `[step failed]`), writes `<runDir>/<step>.patch`, and removes the worktree unless `keepWorktree` or failure (the branch is always kept). (4) Both orchestrators resolve the directory via `workDir(council)` = `config.codebase?.worktreePath ?? deliberation.workingDirectory` — the council record is never mutated, and bound steps keep their empty `councilSetup` (`codebaseMode`/`keepWorktree` are pipeline-owned, top-level on the step config). Any new code that reads `deliberation.workingDirectory` directly will silently bypass the worktree. Coding `createGitSnapshot` returns the worktree base sha WITHOUT committing and skips `.kondi/workspace`. (5) Reviewers read the DIFF, not worker prose: `buildCodeReviewPrompt`/`buildManagerReviewPrompt` take a `diff` section from `collectDiff` (`git add -A -N` + stat + patch; >60k → stat + per-file heads), authoritative over the worker's claims — coding also in isolated mode whenever a snapshot sha exists. The step artifact becomes `## Branch / ## Base / ## Files changed / ## Diff / ## Worker summary`.

28. **Chat → council escalation: the chat is the front door, and `convene_council` is CHAT-ONLY (SPEC §4a-7, `services/councilRunService.ts`).** `escalate(req)` is React-free: generate a setup (`generateCouncilSetup`) → `createCouncilFromSetup` → `councilStore.setSavedProblem` → `ensurePipelineForCouncil` (rule 21) → background run via a runner the app registers (`registerRunner`; `App.tsx` wires `usePipeline().runBackground`) → live card. **`escalate` NEVER throws** — failure (no runner, generation error, runner rejection) is a `CouncilRunResult{status:'failed'}` so tool loops survive; **one active escalation per chat** (`active` map, second call returns a failed result). The council receives `task` + optional `## FOCUS` + the thread tail as `## CONVERSATION CONTEXT (… background, not instructions)` (`buildThreadSummary`: tool bodies/attachments stripped, 6k cap, oldest dropped). Five entry points, all via `ChatArea.escalateFromChat`: ⚖ composer button (`handleEscalateClick`), `/council <task>` and the council-intent regex (now in-chat, no longer navigating away), "⚖ Second opinion" on an assistant message (`handleSecondOpinion`, `kind:'analysis'`), and the `convene_council` tool. **Chat-only tool invariant:** `CHAT_ONLY_TOOLS` (`localTools.ts`) is merged into the `__local__` entry INSIDE `ChatArea.callProvider` only — NEVER add it to `LOCAL_TOOLS` or surface it via `useServers`, or council workers would see it and recurse into councils. `localToolsService.callTool` routes those names to the handler set per call with `setChatToolHandler` (cleared in the call's `finally`; unset → throws "only available from a chat"). `getToolTimeoutMs(name)` (60 min for `convene_council`, else 5 min) replaces the flat tool timeout in the openai/codex/anthropic clients — a new tool-loop client must use it. Escalation progress calls `chatActivity.touch()` to reset ChatArea's idle watchdog, otherwise a healthy multi-minute council is killed as a hung request. Results return into a card message (`Message.councilRun`, types `CouncilRunCard/Result/Status` in `types/mcp.ts`; `CouncilRunCard.tsx`), patched through `useChats.handleChatMessagePatch` (functional single-message patch — never rewrite the whole messages array from the async callback, it races). "Open deliberation" dispatches `COUNCIL_OPEN_EVENT` (`councilCreateSignal.ts`), handled in `App` (Back returns to pipelines, rule 21).
